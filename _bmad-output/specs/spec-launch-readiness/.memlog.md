- (note) Sources: finalized ARCHITECTURE-SPINE (14 ADs, status final) from the 2026-09-19 architecture run; 12 OpenSpec specs in openspec/specs/; adversary gate review that framed this cluster as the launch prerequisite.
- (direction) Scope decision (user): this spec covers everything in the spine Deferred section - consensus core (AD-10 through AD-14), root-sync precedence rewrite, AD-9 error flow, AD-8 config split, recursive key sort, key custody, electron-app dev-storage clause. Sybil and ENR/relay rows remain non-goals.
- (capability) CAP-1 Chain-derived account state (AD-10): exactly one core state-transition function applies accepted blocks to account state computed purely from chain contents, so any node holding the same chain derives the same state. Success: replaying a block sequence (rewards plus user txs) into a fresh core yields balances exactly equal to starting + rewards - sent, with fees to the miner.
- (capability) CAP-2 User transactions accepted and propagated: a user can send a transaction from a funded account and have it accepted into the pool, mined, and reflected in the recipient balance on every node. Success: two-node test - tx from A to B is mined; both nodes report B balance increased by the amount; chain grows past height 3 with user-tx blocks.
- (capability) CAP-3 Deterministic miner lottery (AD-4, AD-invariant family per AD-11): a node determines lottery wins by self-evaluating Crypto.hash(prevBlockHash hex, publicKey hex) less than threshold with fixed family and encoding. Success: property test - winner decision is identical across independently computing nodes for the same inputs; varying p scales the win rate proportionally within a statistical band.
- (capability) CAP-4 Autonomous mining (AD-4): a node mines on a fixed re-check interval without external triggers; the HTTP mine endpoint remains a dev-only convenience. Success: with autonomous mining on, blocks appear at the configured interval with no HTTP calls; with it off, no blocks are produced.
- (capability) CAP-5 Canonical block contents (AD-12): one canonical form for block contents - exact hash input field set (height, uuid, timestamp, miner, lastHash, data) and total order on data (timestamp ASC, uuid ASC). Success: two independently built blocks with identical logical contents hash identically regardless of data insertion order; the field set is versioned so any change is a flagged hard fork.
- (capability) CAP-6 Pool sync without data loss or remote authority (AD-13): pool sync applies only while the local chain is empty; otherwise peer pool contents merge additively by uuid; the root setMap full-replace is removed. Success: tests - empty-chain node adopts synced pool; non-empty-chain node merges (uuid union, local entries survive); no full-replace code path remains.
- (capability) CAP-7 Deterministic fork resolution (AD-14): on equal-length chains the system builds on the lower block hash at the divergence point and rejects incoming equal-length chains. Success: presenting both forks to two nodes leaves both on the lower-hash chain; incoming equal-length is rejected with a typed error.
- (capability) CAP-8 Root bootstrap is empty-chain-only (deferred root-sync rewrite): root state and pool sync apply only while the node chain is empty, so bootstrap is never an override. Success: a node with a non-empty chain ignores root sync; blockchain-core Chain-sync precedence requirement is rewritten to match.
- (capability) CAP-9 Typed error flow (AD-9): core throws typed errors and the app layer maps them to the documented HTTP envelope (type error, code, message). Success: integration tests - duplicate tx 409, insufficient balance 402, invalid hash or signature 400, unexpected 500 each produce the envelope; no HTTP status logic in core (static check).
- (capability) CAP-10 Configuration ownership split (AD-8): each config value has one owner - chain semantics in src/main/config.js, network in src/config.js, renderer values via the preload bridge (getApiPort); the mining re-check interval is an app-semantic value distinct from VALIDATION_RATE. Success: renderer has no direct imports of src/config (static check); preload exposes getApiPort.
- (capability) CAP-11 Canonical hashing (crypto-utils gap): Crypto.hash sorts object keys recursively and pins the documented scalar-argument behavior. Success: unit tests - nested key order is invariant; scalar behavior matches the documented contract; crypto-utils spec updated to match.
- (capability) CAP-12 Key custody (deferred): a user can export an encrypted wallet backup, restore it on a new install, and the system detects a corrupted wallet file instead of silently generating a new identity. Success: export, wipe wallet dir, restore, same public key; corrupted file yields a typed error, not a fresh key; wallet spec updated.
- (capability) CAP-13 OpenSpec reconciliation (deferred rewrites): the six affected specs (blockchain-core, transaction-miner, api-endpoints, crypto-utils, wallet, electron-app) are rewritten to the implemented target state. Success: openspec verify passes; every rewritten requirement traces to an AD; no spec states behavior the code no longer has.
- (constraint) C1 Headless core (AD-1): UI to Shell to App to Core, one-way deps; no HTTP or IPC knowledge in core. C2 Symmetric network (AD-2): every node runs the same code, no node is privileged, longer-valid-chain wins. C3 No purchasable privilege (AD-3): equal mining eligibility, stake is a neutral lock that gates nothing. C4 Root is bootstrap-only (AD-5): root state and pool sync are empty-chain-gated; no standing authority. C5 Lottery family pinned (AD-11): fixed-odds threshold Crypto.hash(prevBlockHash hex, publicKey hex) less than threshold, self-evaluated, both inputs hex strings, argmin-over-known-peers excluded; only probability p is free (core config). C6 Canonical block contents (AD-12): hash input field set exactly (height, uuid, timestamp, miner, lastHash, data); data in total order (timestamp ASC, uuid ASC); any field-set or order change is a hard fork; same rule for tx signature inputs. C7 Pool sync (AD-13): empty-gated, then additive merge by uuid, never full replace. C8 Equal-length forks (AD-14): build on the lower block hash at the divergence point; incoming equal-length chains rejected. C9 Deterministic state-transition (AD-10): exactly one core state-transition function applies accepted blocks to account state derived purely from chain contents; validation is pure over chain contents and never reads local disk. C10 Money uses big.js with integer units, fee is amount divided by 1000. C11 Errors follow AD-9 with the envelope type error code message and the status map duplicate 409, insufficient balance 402, invalid hash or signature 400, unexpected 500. C12 Complexity max cyclomatic 8. C13 Testing via npm test only, never npm run test:ci.
- (direction) Non-goals: NG1 Sybil resistance and multi-wallet mechanics - deferred to a separate future request, boundary locked by AD-3. NG2 Purchasable mining privilege or staking-yield - ruled out by AD-3. NG3 Root as an ongoing authority or a second source of truth - ruled out by AD-5. NG4 Proof-of-work or difficulty-based mining - ruled out by the lottery family in AD-11. NG5 Any change to the canonical hash field set without a flagged hard fork - ruled out by AD-12.
- (direction) Success signal: two independent nodes started from the same genesis converge on the same chain and each accepts the other user transactions past height 3; the wallet sends a user transaction that is mined and reflected in the recipient balance on both nodes; no node holds privileged authority over the other.
