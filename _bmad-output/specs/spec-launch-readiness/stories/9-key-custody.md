## Intent

**Problem:** A corrupted or lost wallet file is undetectable: `Wallet` always generates a fresh key pair in the constructor, and the HOC `retrieveThrough()` that `api.js` uses at startup either `JSON.parse`s whatever is on disk straight onto the freshly generated identity (a parseable-but-garbage file silently overwrites it — silent identity corruption) or throws an untyped error (unparseable file — app crash with no diagnosis). There is also no way to back the key pair up: lose `~/.succinctcoin/wallet` and the identity (and everything it controls) is gone. CAP-12 requires export → wipe → restore yielding the same public key, and a corrupted wallet file yielding a typed error, not a fresh key.

**Approach:** Give `Wallet` a strict `load()` that replaces the HOC `retrieveThrough` at the production call site (file missing → persist generated keys, as today; file present → validate JSON shape and cross-derive the public key from the private key, throwing a typed `corrupted-wallet` on any failure — never assigning, never falling back). Add an encrypted export/restore of the key pair (password-derived key via scrypt, aes-256-gcm authenticated cipher, human-readable `succinctcoin-backup-v1:` prefix; failures are typed `invalid-backup`), exposed through the `Wallet` API and two thin IPC entry points following the existing `/api/wallet-info` handler pattern. Update the wallet OpenSpec spec's backup-and-recovery requirement to the implemented contract.

## Boundaries & Constraints

**Always:**
- On-disk custody format is unchanged (ratified): the wallet file stores the raw identity as JSON with hex `privateKey`/`publicKey` — exactly what the HOC `store()` writes today. Only the READ path becomes strict.
- The wallet file's valid shape: `privateKey` a 64-character lowercase hex string; `publicKey` a 130-character hex string with `04` prefix (uncompressed secp256k1 — the form `Wallet` always stores).
- Validity is not just shape: the stored `publicKey` must equal the key derived from the stored `privateKey` (`@noble/secp256k1` `getPublicKey(secretKey, false)`). A mismatched pair is corruption.
- The backup is the encrypted JSON payload `{ v: 1, privateKey, publicKey }` (single construction site; `v` is the format version). Cipher: `aes-256-gcm` with a random 12-byte IV; key: `scryptSync(password, 16-byte random salt, 32, { N: 16384, r: 8, p: 1 })`. Wire format: `succinctcoin-backup-v1:` + base64(salt ‖ iv ‖ ciphertext ‖ 16-byte tag). Decodable structure is ≥ 44 bytes before base64.
- All node built-ins (`crypto`) only — zero new dependencies (pinned-versions policy).
- Backup operation failures (wrong password, tampered ciphertext, malformed/undecodable backup, wrong version, failing shape/derivation checks, empty or non-string password) throw `BlockchainError` with code `invalid-backup`. Wallet-file corruption throws with code `corrupted-wallet`. Both messages are human-readable and name what failed.
- New codes are added to `ERROR_CODES` in `src/main/blockchain/errors.js`. The AD-9 HTTP mapper is NOT extended: these codes surface at startup and the IPC surface, not HTTP routes (an unexpected route throw already degrades to 500/`unexpected-error` via the existing default).
- The IPC entry points follow the `/api/wallet-info` precedent (`ipcMain.on` + `event.returnValue` in `src/main/api.js`; logic in exported, dependency-injected helpers so they are testable without `init()`): `walletExport({ wallet, password })` → `{ backup }` or `{ code, message }`; `walletRestore({ wallet, backup, password })` → `{ publicKey }` or `{ code, message }`. The passphrase crosses only via the IPC argument — never an HTTP request body.
- A corrupted wallet is FAIL-FAST: `load()` throws before assigning any field, and the startup path (`api.init`) propagates the error (no catch-and-continue, no fresh identity). Recovery is an explicit programmatic act: restore the backup with its password.

**Never:**
- No change to the wallet file FORMAT or to `store()`/`stringify()` (the HOC serialization stays the on-disk contract).
- No new renderer components or preload changes (no UI test harness exists; the renderer-ui track owns UI — the IPC surface is this story's user-reachable ending).
- No HTTP routes for export/restore. No change to `Account`, the miner, the core, or the libp2p peer-identity derivation.
- No auto-discovery of backups, no key rotation, no multi-wallet mechanics (NG1), no change to which key the libp2p identity uses.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| LOAD_FIRST_RUN | no wallet file exists | `load()` persists the generated keys (HOC `store()`) and returns the wallet holding them | No error |
| LOAD_VALID | wallet file = JSON of a valid pair | `load()` assigns the file's keys; the wallet's identity is the one on disk | No error |
| LOAD_NOT_JSON | wallet file = non-JSON content | no assignment; typed error | throws `corrupted-wallet` |
| LOAD_BAD_SHAPE | wallet file = parseable JSON missing keys / non-hex / wrong lengths | no assignment; typed error | throws `corrupted-wallet` |
| LOAD_KEY_MISMATCH | wallet file = well-shaped JSON whose `publicKey` does not derive from its `privateKey` | no assignment; typed error (this is the silent-overwrite hole the strict load closes) | throws `corrupted-wallet` |
| EXPORT_VALID | a wallet with a valid identity, non-empty string password | returns `succinctcoin-backup-v1:` + base64; the decoded structure is ≥ 44 bytes | No error |
| EXPORT_BAD_PASSWORD | empty / non-string password | no backup string produced | throws `invalid-backup` |
| RESTORE_SAME_KEY | backup from wallet A; wallet file wiped; fresh wallet B (new random keys) | `restoreBackup(backup, password)` assigns A's keys to B; `B.publicKey === A.publicKey` (CAP-12 success) | No error |
| RESTORE_WRONG_PASSWORD | valid backup, different password | no assignment; typed error (GCM auth failure) | throws `invalid-backup` |
| RESTORE_TAMPERED | one flipped ciphertext byte | no assignment; typed error | throws `invalid-backup` |
| RESTORE_MALFORMED | wrong prefix / invalid base64 / truncated / payload `v ≠ 1` / failing payload validation | no assignment; typed error | throws `invalid-backup` |
| IPC_EXPORT | `walletExport({ wallet, password })`, valid password | `{ backup: '<string>' }` | `{ code: 'invalid-backup', message }` on failure |
| IPC_RESTORE | `walletRestore({ wallet, backup, password })`, valid inputs | `{ publicKey: '<130-hex>' }` | `{ code: 'invalid-backup', message }` on failure |

## Code Map

- `src/main/blockchain/errors.js` -- `ERROR_CODES` + `BlockchainError` (story 7); add `CORRUPTED_WALLET: 'corrupted-wallet'`, `INVALID_BACKUP: 'invalid-backup'`.
- `src/main/blockchain/wallet.js` -- the `Wallet` class (CJS requires inside an ESM file; `Obj2fsHOC`-wrapped export). The HOC provides `stringify`/`store`/`retrieve`/`retrieveThrough` on the subclass prototype; `api.js` and `wallet.test.js` call `retrieveThrough()` today. Add: `load()` (the strict replacement — sync file check + read, async `store()` only on the missing-file path), `exportBackup(password)`, `restoreBackup(backup, password)`, plus private module-level helpers kept small (`decoding`, `decryption`, `payload validation` — each well under cyclomatic 8; the class methods stay thin). `restoreBackup()` is a sync method: after the validation chain passes it assigns the restored pair AND persists it to the wallet file with a synchronous write of the byte-identical HOC-`store()` output (the `key` property is transient — the persisted JSON carries only `privateKey`/`publicKey`; the class does NOT hold a `key`-stripping flag, so the persist helper must compute the exact `stringify()`-minus-`key` content itself, and must NOT call the async HOC `store()` — the IPC `event.returnValue` must answer inside the synchronous dispatch, and the HOC `store()` also deletes/re-sets `this.key`). CAP-12's export→wipe→restore success only holds if the restored identity is durable: without the persist, a restart re-runs the strict `load()` on the still-wiped (or still-corrupt) file and fails or re-generates a fresh identity — the recovery would undo itself.
- `src/main/api.js` -- `init()` line 35 is the only production `retrieveThrough` call site (`wallet = await (new Wallet()).retrieveThrough()`) — it becomes `load()`. Add the exported `walletExport`/`walletRestore` helpers (the `transact` DI pattern from story 7: collaborators passed in; each wraps the wallet call in one try/catch and shapes `{ backup }` / `{ publicKey }` / `{ code, message }`) and the two `ipcMain.on` one-liners next to `/api/wallet-info` — each takes the same single-arg form as the existing handlers, destructured per channel: `/api/wallet-export` takes `({ password })`, `/api/wallet-restore` takes `({ backup, password })`.

## Tasks & Acceptance

**Execution:**
- `src/main/blockchain/errors.js` -- add the two codes -- the typed-error surface for key custody (AD-9 primitive, core throws, no HTTP knowledge).
- `src/main/blockchain/wallet.js` -- add `load()` (strict: exists? → `store()` the generated keys; else read → JSON parse → shape checks → cross-derive public from private → assign; every failure throws `corrupted-wallet` before any assignment) and the backup pair (`exportBackup`, `restoreBackup`) with their helpers -- the custody capability lives on the identity owner, not the app layer. `restoreBackup()`'s success path assigns the restored pair AND persists it to the wallet file (synchronous byte-identical-`store()` output; the HOC's async `store()` is unavailable inside the synchronous IPC dispatch) so the restored identity survives a restart — CAP-12's export→wipe→restore success requires durable recovery (see Design Notes: "Why restore persists (rli-1)").
- `src/main/api.js` -- switch `init()` to `load()`; add the `walletExport`/`walletRestore` helpers + two `ipcMain.on` handlers -- the IPC is the user-reachable surface; the exported helpers keep the logic testable per the story-7 `transact` pattern.
- `src/main/blockchain/wallet.test.js` -- move the two `retrieveThrough()` call sites to `load()`; add the matrix rows for strict load (including the `LOAD_KEY_MISMATCH` cross-derivation case) and export/restore (including the CAP-12 export→wipe→restore success flow) -- corruption and restore are this story's acceptance surface.
- `src/main/api.test.js` -- add the helper rows (success + failure shapes) -- the IPC contract is pinned by a test.
- `openspec/specs/wallet/spec.md` -- rewrite only the "Wallet backup and recovery" requirement to the implemented contract -- CAP-12's "wallet spec updated to match".

**Acceptance Criteria:**
- Given a wallet with persisted keys, when its wallet file is wiped and the encrypted backup is restored with the correct password, then the restored wallet has the same public key (identity preserved through backup/restore) AND the restored identity is written to the wallet file (re-reading the file after restore yields exactly `{ privateKey, publicKey }`) — the recovery survives an app restart (a fresh `load()` on the restored file installs the SAME identity; it neither fails nor generates a fresh key).
- Given a corrupted wallet file (non-JSON, malformed JSON, or a key pair that fails cross-derivation), when the app loads the wallet at startup, then it receives a typed `corrupted-wallet` error and no fresh identity is used.
- Given the IPC surface, when a caller exports with a password, then a restorable `succinctcoin-backup-v1:` string is returned; a wrong password or tampered backup on restore yields the typed `invalid-backup` shape, not an exception escape or a silent state change.

## Design Notes

**Why strict load on `Wallet` rather than patching the HOC.** `obj2fs-hoc@1.3.2` `retrieveThrough()` does `JSON.parse` + `Object.assign(this, obj)` with no validation; subclass-prototype methods cannot be overridden by the wrapped class, so the strict path is a new named method (`load()`) and the single production call site (`api.js` `init`) plus the test call sites move to it. `store()`/`stringify()` stay untouched — the on-disk format is ratified and other code (and user wallet files) depend on it.

**Cross-derivation is the load's keystone check.** Shape checks alone would accept a tampered file whose `privateKey` is valid-looking hex but does not match its `publicKey` — exactly the silent-overwrite hole: today `Object.assign` would install such a pair and the wallet would "work" as a different-looking identity whose signatures no longer match what the network recorded. Deriving `getPublicKey(secretKey, false)` (uncompressed, the stored form) and comparing closes it. In jest the `@noble/secp256k1` mock caches keys by private key, so test fixtures must pass through the mock's `keygen()` (or a prior `getPublicKey`) before `getPublicKey` derivation is valid — a fixture built from raw hex bytes would throw "Private key not found in cache".

**Why the backup is authenticated, not just encrypted.** aes-256-gcm's auth tag is what turns "wrong password" and "tampered backup" into detectable typed failures instead of silent garbage: a flipped byte fails decryption, so `invalid-backup` is honest. scrypt keeps an offline brute-force of a leaked backup costly (N=16384/r=8/p=1 is the RFC 7914-recommended minimum; the 16 MB scrypt memory stays under node's 32 MB `maxmem` default).

**Why IPC, not HTTP, and why no renderer in this story.** The passphrase is a secret: crossing it in an HTTP request body (even localhost) or baking it into a route is a worse custody story than the synchronous IPC argument the app already uses for wallet data (`/api/wallet-info`). The exported helper + one-line handler split follows the story-7 `transact` pattern so the logic is testable without running `init()` (which starts the miner and libp2p discovery — unreachable from `api.test.js` today). The IPC handlers are the user-reachable ending of this story; building export/restore UI (dialogs, file save, bridge whitelist changes, renderer tests) is the renderer-ui track's job — a component harness does not exist in this repo yet.

**Why restore persists (rli-1).** A restore that only assigns in-memory keys is not recovery: `api.init` re-runs the strict `load()` from disk on the next start, so after wipe→restore the file is still gone (fresh identity re-generated on restart) and after corrupt→restore the file is still corrupt (startup crash on restart) — either way the recovery undoes itself at the restart boundary, and the in-module `account`/libp2p identity built at `init` stays on the pre-restore key. Durable recovery is the single defensible reading of CAP-12's "export → wipe → restore yielding the same public key." The persist is a SYNCHRONOUS write of the byte-identical HOC-`store()` output (delete-transient-`key`, then `stringify()`, then `fs.writeFileSync` on the same resolved path): the HOC `store()` itself is async (`fs.outputFile`), cannot be awaited inside `ipcMain.on`'s synchronous `event.returnValue` dispatch, and additionally deletes/re-sets `this.key` (a state side effect the thin restore path should not take). A sync write of the same bytes is observable-identical to `store()` on disk — the ratified format pin holds (asserted by the `RESTORE_SAME_KEY` file re-read row).

**Storage/test isolation.** Under jest `JEST_WORKER_ID` is set, so `ROOT` is `.test/` (`src/main/config.js`) and the wallet file is `.test/wallet`. Only `wallet.test.js` touches that file (grep-verified); the new rows must keep that property (explicit `rm`/writes per row, no new suites calling `load()` at import scope) so the parallel-worker layout stays race-free. Two known co-writers must be neutralized: `crypto.test.js`'s `isPublicKey` fixture (pre-existing `retrieveThrough()` call — replaced by a pure constant per the Code Map) and the new `api.test.js` `walletRestore` round-trip row (its wallet persists the restored identity — kept OFF the shared file via a worker-unique `setKey()` tmp path, so no new cross-suite surface is created). `block.test.js:119` (`await wallet.store()`) is a pre-existing third writer left untouched by this story (deferred — see Spec Change Log).
